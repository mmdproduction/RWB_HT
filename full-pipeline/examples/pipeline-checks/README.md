# Задания для проверки пайплайна

Каждый файл `01-…06-…` — готовое ТЗ для отдельного запуска. Вставляйте в панель **только содержимое выбранного файла**, а эту инструкцию используйте при проверке результата. Набор подготовлен по текущему контракту генерации; фактические результаты нужно зафиксировать после запуска с рабочей моделью и Docker.

## Порядок запуска

| № | Файл | Что проверяет | Ожидаемое завершение |
|---|---|---|---|
| 1 | [Калькулятор](01-calculator.md) | Основное действие через API, дробные числа, ошибки, экран без входа | `succeeded` и ручная приемка |
| 2 | [Конвертер температуры](02-temperature.md) | Другая предметная логика, формулы, границы и округление | `succeeded` и ручная приемка |
| 3 | [Задачи команды](03-team-tasks.md) | CRUD, права, типы полей, сводка, сохранность | `succeeded` и ручная приемка |
| 4 | [Остатки склада](04-stock-value.md) | Вычисления из БД, денежные значения, серверная валидация | `succeeded` и ручная приемка |
| 5 | [Парковка](05-parking.md) | PostGIS, жизненный цикл сеанса, события, предупреждение | `succeeded` и ручная приемка |
| 6 | [Противоречивое ТЗ](06-conflicting-requirements.md) | Критический вопрос и остановка до генерации | `blocked` на анализе |

Начните с № 1 и № 3. Затем выполните оставшиеся задания по одному: генерации используют одну модель и создают отдельные приложения. Один запуск соответствует одному ТЗ.

Открыть панель: <http://127.0.0.1:8090>. Альтернатива — из корня `full-pipeline` отправить выбранный файл существующим скриптом:

```bash
python3 scripts/create_run.py examples/pipeline-checks/01-calculator.md
```

Скрипт только создает запуск через API на порту 8100 и печатает `runId`; за завершением следите в панели. Для другого задания замените имя файла. Отправка всех заданий одним текстом не проверяет независимые прогоны.

## Общая приемка успешного запуска

Для заданий № 1–5:

1. Запуск выходит из очереди и получает `succeeded`. Проверьте реальные отчеты стадий analysis, design, generation, build, test, security, deploy и documentation. Пропущенная проверка или `not_run` не считается прохождением.
2. Откройте ссылку приложения. Выполните основное действие из ТЗ и проверьте все приведенные числовые примеры. В инструментах разработчика браузера убедитесь, что действие обращается к API и результат соответствует ответу сервера.
3. Проверьте ошибки ввода, исправление после ошибки, сброс там, где он предусмотрен, и отсутствие повторных отправок во время запроса. Для сетевой ошибки временно включите режим Offline в инструментах браузера, отправьте действие, затем верните сеть и повторите.
4. Проверьте экран при ширине 360 пикселей и на компьютере: поля и основная кнопка доступны, текст и результат читаются, горизонтальная прокрутка не мешает работе. В калькуляторе проверьте Enter.
5. Для № 3–5 проверьте права отдельным запросом API с токеном обычной роли: изменение административных данных должно отклоняться с 403. Скрытая кнопка сама по себе не доказывает запрет. Реальные маршруты и формат запросов берите из сгенерированного проекта и сетевых запросов приложения.
6. Для № 3–5 создайте собственную контрольную запись, обновите страницу и убедитесь, что она сохранилась. Затем перезапустите backend и db именно сгенерированного приложения через его Compose-проект, дождитесь готовности и проверьте запись и вычисления снова. Используйте имя Compose-проекта из `reports/deployment.json`; volumes сохраняйте.
7. Скачайте ZIP и откройте вкладку «Файлы». Проверьте наличие исходного `requirements.md`, `app-spec.json`, исходников в `project/`, отчетов и документации. В `reports/pipeline-evidence.json` должны быть свидетельства фактических проверок текущих исходников; в `reports/deployment.json` — адрес приложения.

Предметные примеры для № 3 и № 4 рассчитаны на пустую базу. Автоматическая приемка может оставить свои записи. Выполняйте ручную проверку в отдельной чистой копии сгенерированного проекта либо учитывайте исходные записи при подсчете; не удаляйте данные платформы. Для № 5 завершите прежний активный демо-сеанс и учтите текущее тестовое время перед отсчетом 49/50 минут.

Для № 1–2 дополнительно проверьте `app-spec.json`: `uiMode` должен быть `focused`, `requiresLogin` — `false`, бизнес-сущности и история не требуются. Основной экран сразу показывает инструмент. Успешная сборка с посторонней таблицей записей вместо нужного действия не проходит ручную приемку.

## Приемка противоречивого задания

Для № 6 ожидается `blocked` после анализа с явным критическим вопросом о двух несовместимых требованиях. Сборка и развертывание не должны выполняться. Проверьте `questions` в `app-spec.json` и объяснение в панели. Если модель молча выбрала один вариант, запустила генерацию или вернула `succeeded`, проверка не пройдена. Ответ модели недетерминирован: это проверка фактического поведения, а не гарантия остановки по одному лишь тексту ТЗ.

`succeeded` подтверждает автоматический прогон; соответствие бизнес-ТЗ подтверждается отдельной ручной приемкой. Сбой модели, registry или Docker фиксируйте с названием стадии и логом: такой запуск не подтверждает работоспособность задания. Повтор после устранения причины выполняйте новым запуском.

Эти ТЗ проверяют генерацию и результат приложения. Конкурентное получение заданий, lease/heartbeat, прерывание worker и автоматическое исправление кода проверяются отдельно тестами платформы и управляемыми отказами; случайная ошибка генерации не является воспроизводимым тестом механизма исправления.
