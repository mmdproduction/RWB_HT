# Архитектура агентного пайплайна v2

Запрос пользователя: исправить архитектуру агентной системы, обеспечив соответствие исходной бизнес-задаче и качество приложения. Стек платформы/результата сохраняется. Новая схема заменяет генерацию одного общего патча с собственными тестами.

## Исполнение

Один долговечный worker — исполнитель очереди. Внутри него координатор запускает специализированные агентные задачи с изолированными контекстами и типизированными результатами. Одна Qwen может обслуживать все роли последовательно: сервер ограничивает параллельные обращения. Последовательность задают зависимости артефактов, а не свободный чат агентов.

1. **Business analyst**: исходный запрос → AppSpec с целями, требованиями, источниками, экранами и границами.
2. **Solution architect**: запрос + AppSpec → Blueprint: endpoints, входы/ответы, права, экраны, стабильные testId контролов и покрытие каждого требования.
3. **Acceptance designer**: запрос + согласованные контракты, без исходников реализации → HTTP/UI-сценарии и явные ручные проверки. План фиксируется до кода; авторы кода не могут его менять.
4. **Backend engineer**: предметные C# исходники по Blueprint, только backend/Generated.
5. **Frontend engineer**: предметные Angular исходники по тем же контрактам и UX-плану, только frontend/src/app/generated. Главный экран выполняет бизнес-действия.
6. **Integration reviewer**: независимый от авторов контекст, исходное ТЗ + контракты + фактические исходники. Блокирующие замечания имеют ссылки на требования/файлы и адресата.
7. **Детерминированные инструменты**: компиляция, HTTP, Chromium UI на desktop/mobile, сохранность БД, аудит, запуск. Модель не назначает им успешные статусы.
8. **Acceptance reviewer**: исходный запрос + зафиксированный план + исходники + результаты инструментов → решение о полноте, отклонения и непроверенные ручные пункты. Отсутствующее доказательство не считается passed.

Координатор исправлений выбирает backend/frontend по конкретной диагностике и замечаниям; сами исправления выполняет профильный агент. Контракты и план приемки при этом неизменяемы. На неуспешный этап не более двух автоматических исправлений. Изменение кода аннулирует прежнее подтверждение его проверки; актуальные результаты привязаны к hash предметных исходников.

## Артефакты и наблюдаемость

- reports/agents/graph.json: состояния, зависимости, попытки, входные/выходные хеши и длительности.
- reports/agents/events.jsonl: журнал агентных задач.
- reports/contracts/blueprint.json и acceptance-plan.json: проверяемые контракты до кода.
- reports/reviews/: независимые замечания и решения.
- reports/browser/: Chromium результаты и скриншоты.
- Все материалы доступны через проводник файлов, включая неуспешные попытки. Секреты не передаются агентам и не публикуются.

Публичные восемь стадий API сохраняются для совместимости; внутри них выполняются узлы графа. Переименование этапов не заменяет типизированные контракты, отдельное авторство приемки и фактические инструменты.

## Границы

Ревью исходников одной моделью в разных контекстах не равно независимой экспертизе другой моделью. Chromium проверяет поведение и базовую адаптивность, не гарантирует художественное качество. Ручные пункты перечисляются явно и не объявляются автоматически проверенными. При критической неоднозначности или неисправимом нарушении контракта запуск останавливается. Внешний GitLab остается отдельно настраиваемой интеграцией.

Пользователь ранее запретил дополнительные тестовые прогоны: при реализации v2 новые генерации/тесты не запускаются. Код инструментов предназначен для последующих пользовательских запусков; изменения собираются и передаются с явным статусом проверки.
