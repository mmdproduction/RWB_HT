# Сетевой сбой Docker registry

В предоставленном журнале BuildKit остановился на HEAD-запросе метаданных `postgres:17.9-bookworm` к `registry-1.docker.io`: `net/http: TLS handshake timeout`. Это произошло до сборки приложения. Сообщение Compose о Bake носит информационный характер. По этому журналу нельзя установить, вызван ли timeout маршрутом, прокси, фильтрацией или временной недоступностью registry.

## Изменение пайплайна

- Обычная сборка, сборка кандидатного исправления и сборка перед выпуском повторяются при распознанных временных транспортных ошибках: всего до трех попыток, паузы 5 и 15 секунд.
- Повтор не меняет код, не вызывает модель и не увеличивает attempt стадии либо счетчик модельных исправлений.
- Каждая команда сохраняет отдельный отчет и лог. Потеря lease отменяет ожидание и повтор.
- Ошибка компилятора не повторяется как сетевая; она направляется на исправление кода. Общая ошибка получения метаданных без признаков временного сетевого сбоя сразу блокирует запуск.
- Исчерпание сетевых повторов дает `blocked`, а не ложный успех. Если это случилось при компиляции кандидата, кандидат откатывается существующей транзакцией исправления.

## Проверка и применение

Python-код прошел компиляцию. Добавлены проверки восстановления после timeout, ограничения повторов и отсутствия сетевых повторов для ошибки компилятора; они не запускались по ранее полученному указанию пользователя. Полная генерация и сетевые пробы не запускались. Повторы повышают устойчивость к кратковременному сбою, но не восстанавливают недоступный сетевой маршрут.

Завершенные заблокированные запуски сохраняют свой статус. После применения worker новый запуск использует обновленную обработку. Активный запуск нельзя прерывать обновлением контейнера: сначала нужно дождаться его завершения.

Сохраненный `pipeline-evidence.json` содержит `executionMode: automatic_worker` и одинаковые hash исходников для сборки, приемки и развертывания. Приложение: http://127.0.0.1:32784.

Это подтверждает завершение конкретного автоматического цикла до применения сетевых повторов. Оно не проверяет новую ветку восстановления после timeout и не подтверждает качество интерфейса либо полноту бизнес-ТЗ. Дополнительный запуск для этой проверки не создавался.
