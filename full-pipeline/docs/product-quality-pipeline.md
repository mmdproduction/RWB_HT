# Предметная генерация приложений

## Цель и решение

Поднять качество новых генераций: UI отражает задачу пользователя, frontend и backend согласованы через сохранённый API-контракт, критерии приёмки формируются до реализации. Технический стек, mock-политика и ограничения изменения инфраструктуры остаются фиксированными.

Выбран последовательный конвейер: анализ → план UI/API → независимое планирование HTTP/UI-приёмки → backend → frontend → существующая сборка/приёмка/исправления. Альтернативы: увеличить один промпт (сохраняет перегрузку и самопроверку реализации) или запустить несколько агентов параллельно (добавляет рассогласование и нагрузку на общий Qwen). Новый порядок сохраняет один последовательный поток обращений к модели.

## Контракты

- `product-plan.json`: экраны, элементы управления с data-testid, действия, состояния, направление оформления, API endpoints с JSON Schema входов и примерами ответов. Валидируются ссылки на требования, интеграции и endpoints.
- `domain-acceptance.json` и `browser-acceptance.json`: сценарии предлагаются отдельным вызовом до кода, валидируются и замораживаются. Это разделение ответственности одной модели, а не независимая от модели экспертиза полноты требований.
- Backend и frontend получают один контракт. Изменять приёмку при генерации или ремонте запрещено.
- Генерируемый интерфейс становится главным экраном для всех задач. Готовый парковочный UI удаляется из основной оболочки; проверенный backend парковки сохраняется как доступная возможность, которую предметный API может использовать.
- Проверка браузером входит в будущие запуски пайплайна: декларативные действия через data-testid, бизнес-утверждения, отсутствие необработанных JS ошибок, переполнения страницы на мобильном и настольном экранах, диагностические скриншоты. Из модели не исполняются команды, Python или JavaScript проверок.
- Стек приложения: Angular/Material 20.1.6 PWA; C#14/.NET10; PostgreSQL17.9/PostGIS. Playwright — инструмент приёмки, не зависимость бизнес-приложения.

## Ограничения проверки этой работы

Пользователь ранее запретил дополнительное тестирование. Поэтому агент не запускает тесты, браузерные сценарии и новые запросы генерации Qwen. Новые проверки выполнятся только при последующих запусках пайплайна пользователем. Проверяются компиляция Python, сборка доверенной оболочки и сборка образа worker; отсутствие реального прогона явно отмечается в результате.

Существующие приложения не переписываются. Резервная копия генератора — `backups/generator-before-product-quality-20261031.tar.gz`.

## Детали реализации

- Общая оболочка отвечает только за подключение, демо-вход и сообщения. Единственный основной экран — GeneratedPanel; предметная навигация находится внутри него. Проверенный backend парковки остаётся доступным техническим модулем, но не выбирает пользователю экран.
- Один запуск без повторов выполняет пять логических запросов Qwen: анализ, план, приёмка, backend, frontend. HTTP429 обрабатывается прежними ограниченными повторами; параллельная нагрузка на модель не добавляется.
- Публичный номер попытки стадии не уменьшается при переходе между внутренними шагами. Номер попытки конкретного шага сохраняется в reports/quality/.
- План проверяет связи требований, экранов, действий и mock-провайдеров; HTTP-приёмка должна покрывать успешные ответы каждого спланированного endpoint. Контракт поддерживает ограниченный JSON Schema с явными типами, nullable-полями, вложенными объектами/массивами и границами значений.
- HTTP-сценарии могут сохранять скалярный ID из обязательного поля ответа через capture и использовать его как {{variable}} в следующих шагах. Проверяются источник, тип назначения и отсутствие ссылок на ещё не полученные значения. HTTP204 не требует JSON и не допускает capture.
- Браузерные сценарии явно различают успех, ошибку ввода и отказ провайдера. Каждый успешный клик главного действия должен привести к реальному ответу своего API. Подтверждение одного сценария не подменяет остальные.
- HTTP-предметная приёмка, базовая приёмка и каждый размер браузерного окна используют отдельные чистые БД. Внутри одного размера сценарии должны использовать разные бизнес-ключи; это явно включено в инструкции планирования.
- План, HTTP/UI-сценарии, runner и схемы входят в замороженный hash. Ремонт может менять только предметные C#/Angular-файлы, а не ослаблять приёмку или менять зависимости. Выпуск требует успешной браузерной приёмки на 360px и 1280px.
- Скриншоты и JSON-отчёты сохраняются в project/browser-results/, доступном через существующий проводник файлов. Они не проходят автоматическую экспертную оценку дизайна.

Для браузерного runner выбран официальный образ Playwright Python `v1.64.1-noble` и совпадающий пакет `playwright==1.64.1`, согласно [документации Playwright](https://playwright.dev/python/docs/docker). Это отдельный инструмент приёмки; версии зависимостей бизнес-приложения не менялись.

## Что смотреть в следующем запуске

1. product-plan.json и project/docs/openapi.json — согласованный UI/API-план.
2. reports/acceptance-plan.json — критерии до реализации.
3. reports/quality/generate-backend-*.json и generate-frontend-*.json — отдельные ответы компонентов.
4. project/browser-results/browser-report-360.json, browser-report-1280.json и PNG — фактические результаты браузерной проверки.
5. reports/pipeline-evidence.json — ссылки на выполненную приёмку и совпадение исходников сборки/проверки/выпуска.

Эти результаты появятся только при новом запуске. Наличие кода runner или успешная сборка worker не означает, что новая генерация уже прошла проверку.

## Kafka для новых генераций

Контракт событий выводится из зафиксированного плана без дополнительного запроса к Qwen. REST/UI-план, HTTP-приёмка и отдельная генерация компонентов сохранены. Успешные изменяющие операции и submit-действия обязаны сохранять outbox через доверенный BusinessEvents; завершение подтверждается настоящей доставкой через Kafka и обработкой отдельным consumer. Отклонённые действия не должны создавать событие успеха. Подробности — [kafka-integration.md](kafka-integration.md).
