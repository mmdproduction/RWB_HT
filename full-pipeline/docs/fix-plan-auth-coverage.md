# Пропуск требования входа в плане

Дата: 2026-10-31.

## Наблюдение

Запуск `b6935d4f-d5ee-4c67-83f0-a90c63099c56` по заданию «Задачи команды» остановился на проектировании с `Plan omits requirements: REQ-AUTH-01`.

В `app-spec.json` требование определяет демо-вход с выбором роли. В третьем ответе проектировщика все остальные требования связаны с экранами или API, а `REQ-AUTH-01` пропущено. Вход уже реализован в неизменяемой оболочке `templates/assets/frontend/src/app/app.ts` и `app.html`. При этом контракт ProductPlan учитывает покрытие только через `screens[*].requirementIds` и `endpoints[*].requirementIds`.

## Исправление

Промпт проектирования явно требует покрытия всех идентификаторов и объясняет границу ответственности оболочки: требование демо-входа нужно связать с бизнес-экраном, доступным после входа, и описать это условие в его назначении. Генерировать второй вход или новый API авторизации не требуется.

Ошибка валидатора теперь включает определения пропущенных требований, критерии приемки и указание на допустимый способ учета оболочки. Существующий механизм повторов передает эти данные модели. Пропущенные и неизвестные требования по-прежнему отклоняются; автоматического добавления произвольных связей или исключения авторизации из проверки нет.

## Проверка

`tests/test_product_plan.py`: четыре теста прошли. До исправления два новых теста воспроизводили отсутствие определения требования в диагностике и обратной связи повторного запроса. Дополнительно проверены допустимая связь требования с защищенным экраном и сохранение запрета неизвестных ссылок.

Полный запуск `.venv/bin/python -m pytest -q`: 55 passed, 12 skipped, 2 failed. Оба падения воспроизведены в отдельной временной копии без этого исправления:

- `tests/test_templates.py::test_generated_network_is_isolated_and_checks_are_trusted`: ожидаемый набор сервисов не учитывает Kafka и event-consumer.
- `tests/test_worker.py::test_engine_bounded_repair_and_frozen_acceptance`: фикстура модели возвращает прежний формат генерации вместо нового плана; до исправления кода сборки выполнение не доходит.

Пропущены проверки API с отдельной тестовой БД и интеграционная сборка Docker. Этот результат не подтверждает полный цикл генерации приложения.

Дополнительно проверено реальное исправление третьего неуспешного плана через настроенную `qwen3.8-27b`: один запрос, без повторов. Исправленный ответ прошел `ProductPlan.model_validate(...).validate_spec(...)` для всех 19 требований исходного ТЗ; три экрана, пять API-методов, `REQ-AUTH-01` связано с экраном `task-list`. Вызов использовал 15817 входных и 5387 выходных токенов. Эта проверка выполняла только проектирование, без генерации кода, сборки или развертывания нового приложения.

После проверки отсутствия queued/running-запусков worker перезапущен. Лог подтвердил новый старт процесса; импорт модулей внутри контейнера указывает на исправленные файлы в подключенном рабочем каталоге.

Исходный неуспешный запуск и его артефакты сохраняются без изменений. Новый ответ модели и дальнейшие стадии требуют самостоятельной проверки; текст промпта не гарантирует корректность каждого недетерминированного ответа.
