# Развертывание всего пайплайна на VM

Этот путь переносит панель, FastAPI, worker и PostgreSQL платформы. Генерируемые приложения будут собираться и запускаться уже на VM. Используются текущие Dockerfile/Compose без изменения границ генерации. Старые запуски и база с компьютера не переносятся: это отдельная новая установка.

Выданный SSH-доступ: team19@85.143.113.230, порт 10019. Пароль VM и API-ключ вводятся только у себя в терминале/редакторе; в инструкцию они не включены. Команды ниже — инструкция, удаленное развертывание агентом не выполнялось.

## 1. Проверить VM — на своем компьютере

```bash
ssh -p 10019 team19@85.143.113.230
```

В открывшемся терминале VM:

```bash
cat /etc/os-release
docker --version
docker compose version
python3 --version
docker info
```

Нужны Docker Engine с Compose plugin и работающим daemon, доступ к Docker socket и Python3. Node, Angular, .NET и Python-библиотеки на хосте отдельно устанавливать не нужно: они собираются в контейнерах. Python3 нужен для scripts/setup_env.py, стандартной библиотеки достаточно. Первичная сборка требует исходящего доступа к Docker Hub/Microsoft Registry, npm, NuGet и пакетным репозиториям.

Если Docker отсутствует, установи по официальной инструкции для фактической ОС: [Ubuntu](https://docs.docker.com/engine/install/ubuntu/) или [Debian](https://docs.docker.com/engine/install/debian/). Если нет прав на daemon, команды Docker ниже можно выполнять с sudo. Настройка работы без sudo описана в [Docker post-installation](https://docs.docker.com/engine/install/linux-postinstall/); после добавления пользователя в группу docker требуется новый сеанс входа. На VM организаторов без sudo отсутствие Docker/доступа к daemon должен решить администратор VM.

Затем выйди обратно на свой компьютер:

```bash
exit
```

## 2. Упаковать и передать исходники — на своем компьютере

```bash
cd '/home/evodev/Документы/ChatGPT/RWB хахатон/full-pipeline'
tar --exclude='./.env' --exclude='./.venv' \
    --exclude='./artifacts' --exclude='./repaired-projects' \
    --exclude='./.git' --exclude='./.pytest_cache' \
    --exclude='*/node_modules' --exclude='*/dist' \
    --exclude='*/.angular' --exclude='*/__pycache__' \
    -czf /tmp/rwb-pipeline.tar.gz .
scp -P 10019 /tmp/rwb-pipeline.tar.gz team19@85.143.113.230:rwb-pipeline.tar.gz
```

Локальный .env не копируется: он содержит путь этого компьютера и локальные секреты. VM получит собственные настройки и пароль БД. Предыдущие артефакты исключены, чтобы не передавать гигабайты результатов и старые конфигурации приложений.

## 3. Распаковать и настроить — на VM

```bash
ssh -p 10019 team19@85.143.113.230
mkdir -p ~/rwb-pipeline
tar -xzf ~/rwb-pipeline.tar.gz -C ~/rwb-pipeline
cd ~/rwb-pipeline
python3 scripts/setup_env.py
nano .env
```

Скрипт сам задаст абсолютный PIPELINE_WORKSPACE_ROOT для VM, создаст каталог artifacts и уникальные POSTGRES_PASSWORD/WORKER_KEY. При существующем .env он ничего не перезаписывает; при повторной установке проверь, что PIPELINE_WORKSPACE_ROOT соответствует новому каталогу.

В редакторе измени эти строки (API-ключ подставь свой, без угловых скобок):

```dotenv
LLM_BASE_URL=http://10.10.10.10:4000/v1
LLM_MODEL=qwen3.8-27b
LLM_API_KEY=YOUR_QWEN_API_KEY
PUBLIC_HOST=127.0.0.1
```

Это выданный организаторами приватный Base URL. Он должен быть доступен из сети VM; фактическую доступность покажет QWEN_API после запуска. Адрес localhost:14000 относился к туннелю на твоем компьютере, поэтому переносить его в настройки VM не нужно. Собственную модель/веса Qwen этот проект не устанавливает.

PUBLIC_HOST оставляется 127.0.0.1 для выбранного доступа через SSH. Он меняет текст ссылки на результат, а не интерфейс прослушивания портов. В .env уже будут правильные PLATFORM_API_URL и DATABASE_URL для локальных портов VM; менять их на внешний IP не требуется.

## 4. Запустить — на VM

```bash
cd ~/rwb-pipeline
docker compose up -d --build --wait
docker compose ps
```

Если Docker доступен только с sudo, используй sudo для этих команд. Процесс подготовки настроек при этом оставь под team19.

Для просмотра состояния:

```bash
docker compose logs --tail 100 api worker
```

Сервисы работают в фоне и не зависят от открытого SSH-терминала. При обычной перезагрузке Docker с restart:unless-stopped поднимает контейнеры, если Docker daemon включен при старте системы. Генерируемые файлы остаются в ~/rwb-pipeline/artifacts, база платформы — в именованном Docker volume. Не публикуй Docker socket или БД наружу.

## 5. Открыть панель — на своем компьютере

В отдельном локальном терминале, который нужно оставить открытым:

```bash
ssh -N -o ExitOnForwardFailure=yes \
    -L 127.0.0.1:18090:127.0.0.1:8090 \
    -L 127.0.0.1:18100:127.0.0.1:8100 \
    -p 10019 team19@85.143.113.230
```

- Панель: [http://127.0.0.1:18090](http://127.0.0.1:18090).
- Swagger API: [http://127.0.0.1:18100/docs](http://127.0.0.1:18100/docs).

Порты 18090/18100 на компьютере выбраны отдельно от уже работающего локального пайплайна на 8090/8100. Панель обращается к API через свой nginx, дополнительный проброс 18100 нужен только для прямого Swagger. После закрытия туннеля сервер продолжает работать, но локальные ссылки перестают быть доступны.

## 6. Открыть созданное на VM приложение

Результат получает динамический localhost-порт VM, например 32790. Это другой порт, который туннель панели не пробрасывает автоматически. Для приложения с портом 32790 открой еще один локальный терминал:

```bash
ssh -N -o ExitOnForwardFailure=yes \
    -L 127.0.0.1:19090:127.0.0.1:32790 \
    -p 10019 team19@85.143.113.230
```

Открой [http://127.0.0.1:19090](http://127.0.0.1:19090). Вместо 32790 укажи фактический порт из результата запуска на VM. Локальный порт 19090 остается выбранным тобой; ссылка в карточке показывает порт VM и может отличаться. Для другого результата нужен его собственный проброс или замена правой части туннеля.

## Если нужен публичный адрес для других пользователей

Текущая конфигурация рассчитана на локальную доверенную работу через SSH. Открытие http://85.143.113.230:8090 не обеспечивается: Compose привязывает порты к localhost, а IP/SSH-порт организаторов могут быть шлюзом/NAT. Доступность произвольных внешних портов нужно уточнить у организаторов.

Для публичной панели нужны отдельная авторизация, HTTPS и reverse proxy; для динамических приложений — согласованная маршрутизация. Сам пайплайн дает запуск генераций и доступ к артефактам без пользовательской авторизации, поэтому простое изменение bind на 0.0.0.0 не является полноценным публичным развертыванием. Эта инструкция использует уже работающий SSH-доступ и не требует публикации новых портов.

## Если нужен только готовый результат, без пайплайна

Передай project.zip конкретного запуска на VM, распакуй в отдельный каталог и создай .env с новым DB_PASSWORD (пример есть в .env.example). Затем в этом каталоге:

```bash
docker compose up -d --build --wait
docker compose port frontend 80
```

Открой приложение через SSH-проброс показанного порта аналогично шагу 6. Для работы самого созданного приложения доступ к Qwen не требуется: он нужен генератору.
