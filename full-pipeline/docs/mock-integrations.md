# Mock-интеграции в пайплайне

Для новых приложений внешние платежи, карты, уведомления и сторонние данные заменяются локальными провайдерами. Сам API приложения, его PostgreSQL/PostGIS и Qwen пайплайна остаются настоящими. Реальные платежные, картографические и иные сторонние ключи для приложения не требуются.

## Что генерируется

В AppSpec добавлено `externalIntegrations`: идентификатор, тип (`payment`, `maps`, `data`, `notifications`, `custom`), назначение, requirementIds и операции. Режим допускает только `mock`. Операция содержит типизированные inputFields, валидный inputExample и непустой демонстрационный response. Контракт фиксируется до генерации кода. Платеж требует положительную amount и трехбуквенную currency; карты используют локальные GeoJSON/демо-маршруты, данные — тематические fixtures.

В проект включаются доверенный `backend/MockIntegrations.cs`, таблица `mock_integration_calls`, описание API и `docs/mock-integrations.json/md`. Сервис зарегистрирован в DI как `MockIntegrationProviders`. Предметные обработчики вызывают `await mocks.Call(context, providerId, operationId, request)` и используют результат в реальном бизнес-действии. `request` содержит requestId, input и scenario. Возвращается `MockIntegrationResult(StatusCode, Body)`.

`success` возвращает fixture и сохраненную квитанцию; `declined` дает 402 для платежей либо 422 для других типов, `unavailable` — 503. Невалидные входы дают 400. Повтор того же запроса с тем же ключом возвращает сохраненный ответ, другой запрос с тем же ключом дает 409. Реальные деньги не списываются и сообщения не отправляются. Это симуляция контракта; она не воспроизводит все возможности настоящего сервиса. Встроенный парковочный сценарий по-прежнему использует локальные зоны PostGIS, SVG-карту и подтверждение демо-оплаты; модельные дополнения используют общий провайдер для заявленных новых внешних интеграций.

В интерфейсе показано предупреждение о демонстрационных интеграциях. Сгенерированные исходники не должны содержать прямых внешних HTTP-клиентов/URL; стандартные XML namespace inline SVG разрешены. Backend/db/checks запускаются только во внутренней Docker-сети. Браузер ограничен CSP self. Загрузка образов/зависимостей при сборке и обращение самого пайплайна к Qwen этой политикой не запрещены.

## Приемка

Доверенный integration_checks.py проверяет registry по замороженной спецификации, каждый fixture, отказ, недоступность, идемпотентность и конфликт ключей. После предметной приемки проверяются сохраненные бизнес-вызовы: для каждого провайдера должны быть успешное и отказное обращения. Контрактные прямые вызовы учитываются отдельно и не заменяют бизнес-сценарий. После перезапуска проверяются сохраненные квитанции. Эти команды включены в worker и генерируемый GitLab CI.

Сценарии модели обязаны ссылаться на integrationIds и проверять положительные и отрицательные бизнес-результаты. Это помогает обнаруживать пустые заглушки, но не является формальным доказательством всех требований естественного языка. Полноту fixtures и качество интерфейса нужно оценивать на конкретном приложении.

Счетчики подтверждают обращения к каждому провайдеру, а не к каждой его операции. Идемпотентность квитанции обеспечена доверенным провайдером; идемпотентность и атомарность последующих записей заказа/сессии остаются обязанностью предметного обработчика. Инструкция генератору явно требует стабильного бизнес-ключа и повторного бизнес-сценария; сама квитанция не доказывает отсутствие дублей в произвольном бизнес-коде.

## Роль публичной приемки

Для `requiresLogin=false` роль задает worker по роли интерфейса, даже если модель вернула admin. Тела запросов, ожидаемые статусы и проверки бизнес-результата не ослабляются. Замены фиксируются в `reports/acceptance-role-audit.json`; оригинальный ответ модели остается в generation.json, выполняемый набор — в scripts/domain-acceptance.json. Для обычного публичного приложения роль user; для parking — driver; остальные случаи используют первую неадминистративную роль интерфейса. Контрактные и служебные проверки могут использовать admin отдельно от пользовательских бизнес-сценариев.

## Состояние проверки

Python-код и доверенный .NET backend скомпилированы. Тесты, браузерная проверка, новая генерация Qwen и полный автоматический прогон этой версии не запускались по ранее полученному указанию пользователя. Существующие проекты не переписываются: политика применяется при новом запуске обновленного worker.
