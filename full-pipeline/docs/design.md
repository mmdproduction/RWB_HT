# Полный локальный AI-пайплайн RUSSTECH

Основание: согласованное ТЗ ../.. /RUSSTECH_ТЗ_и_план_16_часов.md и выбранный пользователем вариант A. Пользователь прямо поручил реализовать весь пайплайн. Новые практические решения ниже принимает исполнитель.

## Назначение и границы

Платформа принимает единственный предметный вход — бизнес-требования. Angular-панель вызывает FastAPI; PostgreSQL хранит запуски/попытки/логи/артефакты. Python worker атомарно забирает задание, вызывает Qwen, валидирует модель приложения, создает согласованный проект, проверяет сборку/поведение/зависимости, ограниченно исправляет ошибки и разворачивает результат через Docker Compose. Состояния и фактические отчеты видны в панели.

Результат: Angular 20.1.6 и совместимый Angular Material UI Kit; C#14 / ASP.NET Core .NET10; PostgreSQL17.9/PostGIS; PWA для мобильного интерфейса. Kafka только если действительно необходима. Промышленные платежи, фоновые мобильные GPS и iOS не заявляются.

## Подход

Выбран ранее: проверенные технологические основы плюс генерация предметных частей. Полная свободная генерация всех настроек слишком нестабильна. Только заранее написанная парковочная программа не доказывает переносимость.

Технические шаблоны создаются один раз; Qwen формирует AppSpec и предметные дополнения. Связность задают общая схема, OpenAPI, маршруты, миграции, фиксированные зависимости и Compose. Разные прогоны создают отдельные каталоги и Compose-проекты. Реальная модель не заменяется скрытым mock: тестовые ответы используются исключительно в тестах.

## Размещение

Рабочая область не является Git-репозиторием. Исходный учебный репозиторий содержит незакоммиченные пользовательские файлы вне разрешенной на запись области. Поэтому новая реализация создается в отдельном разрешенном каталоге full-pipeline, исходный проект остается доступным. Код сохраняется без коммитов и публикации; конфигурация GitLab предоставляется, внешнее выполнение подтверждается только при доступном GitLab.

## Контракты платформы

Публичные endpoints: POST /api/runs (202), GET /api/runs (список), GET /api/runs/{id}, GET /api/runs/{id}/logs?after=cursor, GET /api/runs/{id}/artifacts, GET /api/runs/{id}/artifacts/{artifactId}, GET /api/runs/{id}/download (ZIP), GET /api/config (готовность без секретов). /health — жив ли процесс; /ready — доступна ли БД.

Внутренние endpoints требуют X-Worker-Key: POST /internal/jobs/claim с workerId; POST /internal/runs/{id}/heartbeat; POST /internal/runs/{id}/progress; POST /internal/runs/{id}/finish. После claim все изменения требуют leaseToken и workerId. Публичный ввод не выбирает рабочую директорию или команду исполнения.

Статусы запуска: queued,running,succeeded,failed,blocked,interrupted. Стадии: analysis,design,generation,build,test,security,deploy,documentation. Статусы стадий: pending,running,passed,failed,blocked,not_run. Стадия имеет attempt, startedAt, finishedAt, message. Логи имеют монотонный cursor. Повтор eventId идемпотентен. Токены/обращения учитываются по каждому фактическому вызову модели, не по повторной доставке события.

Ответ карточки: runId,requirements,status,createdAt,startedAt,finishedAt,message,appUrl,repositoryUrl,stages[],metrics{inputTokens,outputTokens,modelCalls,retries,durationSeconds},artifacts[]. Секреты исключены.

Остановившийся worker определяется heartbeat и переводится в interrupted. Новый claim не продолжает старый запуск автоматически. Терминальное состояние неизменно, кроме идемпотентного повтора того же завершения. ZIP и выдача файлов ограничены корнем конкретного запуска; симлинки и выход через ../ запрещены.

## AppSpec v1

JSON: schemaVersion (1), title, slug, summary, roles (массив строк), requirements[{id,description,acceptance[string]}], entities[{name,fields[{name,type,required}]}], workflows[{name,description,requirementIds[string]}], capabilities[string], assumptions[string], questions[{question,critical}]. Типы полей: string,integer,number,boolean,datetime. Entity name — PascalCase identifier, field name — camelCase identifier. Slug — ASCII lowercase-hyphen, не путь. Имена уникальны, ссылки валидны, количество сущностей/полей и длины ограничены.

Уточнение после обратной связи пользователя: businessGoal, primaryAction, uiMode (focused/workspace), requiresLogin, screens[{name,purpose,requirementIds}], outOfScope и requirement.sourceQuote. Сущности могут отсутствовать; CRUD, история, сводки и роли не добавляются без бизнес-причины. Исходный запрос передается генерации и исправлению вместе с интерпретацией. В focused-режиме GeneratedPanel — главный предметный экран; вход скрыт для публичного инструмента, используется обновляемый технический токен user, никогда admin. Первичная генерация обязана заменить оба entrypoint-файла backend и frontend.

Файлы доступны независимо от регистрации артефактов: GET /api/runs/{id}/files — живой полный список; /files/content?path= — текстовый просмотр; /files/download?path= — отдельный файл. Каталоги зависимостей/сборки исключены, секретные файлы показаны как закрытые. ZIP собирается из всех публичных файлов запуска, а не только зарегистрированных отчетов. Панель содержит вкладки «Файлы» и «Бизнес-задача» и работает с незавершенными и старыми запусками.

Критические questions блокируют продолжение и показываются пользователю. Требования имеют ID; допущения отделены. Проверка формы JSON не заменяет проверку семантики. Исходные требования сохраняются неизменными.

## Модель и доступ

Организатор сообщил http://10.10.10.10:4000/v1, /chat/completions, qwen3.8-27b. Ключ передается через .env, не коммитится. Если адрес достижим только с VM, пользователь открывает SSH-туннель; пароль SSH в системе не хранится. Недоступность модели дает blocked с диагностикой, а не фиктивную генерацию.

## Реальное выполнение

render_project(spec:dict,destination:Path,run_id:str) создает технологическую основу. Qwen возвращает patch {files:[{path,content}]}; worker принимает только разрешенные исходники, не Dockerfile, Compose, зависимости и тесты приемки. Размеры и пути ограничены. Пользовательские shell-команды из ответов не исполняются.

Сборка/тесты выполняются фиксированными инструментами в контейнерах. Сборочная среда не получает ключ модели и Docker socket. Worker имеет управление Docker для запуска заранее заданных образов/Compose; он предназначен для доверенной локальной среды команды. Артефакты монтируются по одинаковому абсолютному пути на хосте и в worker.

Одна начальная попытка + не более двух исправлений на стадию. После исправления повторяются затронутые проверки; перед успехом выполняется проверка основного сценария. Проверки не удаляются моделью. Отчеты содержат команды, return code, диагностические ссылки, находки и not_run/blocked при невозможности исполнения.

Документы системного анализа, продукта, архитектуры, данных, API, запуска, пользователя, разработчика, тестов, безопасности и ограничений генерируются по реальной модели и результатам. Каждый проект имеет .gitlab-ci.yml с действительными командами; локальный автоматизированный исполнитель обеспечивает воспроизводимый эквивалент при недоступном runner. Не утверждать выполнение внешнего GitLab без запуска.
